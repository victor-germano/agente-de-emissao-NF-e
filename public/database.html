4 colunas órfãs, documentadas sem esconder: side_effects, provider, currency e cancelled_at existem na tabela mas não são lidas nem escritas pelo código atual (SupabaseInvoiceRepository.ts). Vieram de uma implementação paralela que foi descartada durante o desenvolvimento — as migrations que as criaram nunca foram revertidas. Não quebram nada (o código simplesmente não referencia essas colunas), mas um schema de produção de verdade deveria limpar isso numa migration de remoção.

Por que invoices/invoice_audit_log estão com 0 linhas

Não é um bug — é o estado real da configuração atual. patients/doctors/consultations têm dados porque foram inseridos diretamente no banco. Já invoices e invoice_audit_log só recebem escrita quando o app roda com SUPABASE_SERVICE_ROLE_KEY configurada — e essa chave nunca foi preenchida no .env local (é secreta, só pode vir do dashboard do Supabase, nunca de automação). Toda simulação feita até agora rodou no fallback em memória. O schema existe e está pronto — só falta essa credencial para o app passar a escrever aqui de verdade.

Segurança (Row Level Security)

RLS habilitado nas 5 tabelas, com zero policies definidas — a chave anon/pública não tem nenhum acesso por padrão (nega tudo, não abre nada). O backend só consegue ler/escrever porque autentica com a service_role key, que ignora RLS deliberadamente — é assim que um backend deve acessar dados protegidos, nunca com a chave anon. Nenhum client (app mobile, painel público) teria acesso direto às tabelas sem passar pela API.
