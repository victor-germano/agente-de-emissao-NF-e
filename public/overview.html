Avaliação ponto a ponto — Seção 3 do documento ("Pontos em Aberto")

1. Arquitetura exata Stripe → n8n → Supabase → App✅ decidida

Implementada com uma escolha deliberada: o app recebe os webhooks diretamente (sem passar pelo n8n), trazendo idempotência/retry para código testado. Supabase é a peça de persistência real. Vale discutir essa escolha na entrevista.

2. API oficial da Prefeitura ou RPA/headless?✅ pesquisado e respondido

Existe API oficial, direta, sem necessidade de RPA — confirmado lendo o manual técnico real da Sigiss/Marília: webservice SOAP em marilia.sigiss.com.br/.../sigiss_ws.php?wsdl (GerarNota, CancelarNota, ConsultarNotaValida), autenticado por CCM+CNPJ+senha no payload (não certificado), com idempotência nativa (id_sis_legado). Mas o manual é de 2012 e a cidade está em transição para o padrão nacional de NFS-e (obrigatório desde 01/01/2026 pela LC 214/2025) — por isso a recomendação prática continua sendo um gateway. Comparei preço/sandbox/documentação real de Focus NFe, eNotas e NFE.io (não estimado) — Focus NFe vence: único com suporte a Marília confirmado por escrito, trial grátis e ilimitado, sem trava de contrato. Detalhe completo com fontes no README.md. NFSeClient isola essa decisão; o mock já simula o esquema real de autenticação da Focus NFe (HTTP Basic Auth).

3. Regras de fallback/erro na emissão✅ resolvida

Retry com backoff exponencial, erros não-retryable interrompem na hora (ex: credencial inválida), status "failed" + motivo, alertas ativos, recuperação de notas travadas, trilha de auditoria completa.

4. Automação do segundo gateway (Pix/parcelado)⚠️ parcial

O próprio documento já classifica como "fora do escopo imediato". Endpoint, schema e pipeline completos já existem (POST /webhooks/gateway2); falta a integração com um gateway real quando ele existir.

5. Formato de retentativa e alertas✅ resolvida

Backoff exponencial configurável, AlertNotifier disparando em toda falha (emissão, dados inconsistentes, estorno desconhecido, reconciliação), consultável via GET /alerts, com métricas de saúde geral.

Resiliência do fluxo de emissão
1

Alertas ativos em falha

Toda falha (emissão, dados inconsistentes, estorno desconhecido, reconciliação) dispara alerta — GET /alerts.

2

Recuperação de notas travadas

Varre invoices presas em "processing" (crash mid-emissão) e reprocessa, periodicamente ou sob demanda.

4

Reconciliação Stripe × notas emitidas

Compara pagamentos aprovados no gateway com notas existentes, preenchendo o que o webhook não entregou.

5

Cancelamento por estorno

charge.refunded localiza a invoice e cancela a NFS-e já emitida, evitando nota órfã.

7

Corrida na idempotência corrigida

findOrCreate atômico — testado com Promise.all — elimina duplicidade sob concorrência real.

16

Token de API simulado + retry inteligente

Erros não-retryável (credencial inválida) param na 1ª tentativa em vez de insistir à toa.

19

Alerta de SLA de emissão

Se emissionDurationMs passar de EMISSION_SLA_MS (default 5s), dispara alerta "warning" mesmo com a nota emitida com sucesso — sinal de degradação antes de virar falha.

Segurança & produção
3

Assinatura do webhook Stripe

Reimplementa o esquema real (t=timestamp,v1=hmac), ativado via STRIPE_WEBHOOK_SECRET.

11

Autenticação por API key

ADMIN_API_KEY protege /invoices, /alerts, /metrics, /debug/*.

12

Rotas de debug fora de produção

NODE_ENV=production desabilita /debug/* por completo (404).

14

Graceful shutdown

SIGTERM/SIGINT esperam o servidor HTTP drenar (com teto de 5s) e as emissões em background terminarem antes de encerrar.

17

Fail-fast em produção

NODE_ENV=production sem ADMIN_API_KEY ou STRIPE_WEBHOOK_SECRET configurados: o processo recusa subir, em vez de só avisar no log.

Persistência & observabilidade
6

Persistência real (Supabase)

Projeto real criado, schema aplicado (5 tabelas, RLS habilitado). Troca automática in-memory ↔ Postgres.

8

Trilha de auditoria imutável

Cada transição de estado vira registro append-only — GET /invoices/:id/audit.

9

Ack rápido no webhook

Responde 202 em "processing" na hora; emissão continua em background.

10

Métricas básicas

Contadores + latência de emissão — GET /metrics.

13

Logging estruturado

JSON por evento em vez de texto solto, pronto para uma ferramenta de observabilidade real.

15

Health check real

Testa conectividade real com o Supabase (quando configurado) e também conta notas presas em "processing" há tempo demais — responde 503 se algo estiver errado, não só "ok" fixo.

18

Tempo de emissão rastreado

Cada nota guarda issuedAt e emissionDurationMs (do pagamento até a nota sair, incluindo retentativa) — visível por nota em GET /invoices e agregado em GET /metrics, persistido no Supabase.

Rodar: npm install → npm run dev → painel de simulação.

Verificar: npm run typecheck, npm test (64 testes), ou bash scripts/demo.sh para a simulação automática completa de ponta a ponta.
